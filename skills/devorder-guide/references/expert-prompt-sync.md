# 转达硬契约（与 devorder-guide Skill 第 3.5 节同文同义——两通道必须一致）

consult/draft_plan/publish_plan 返回后，**必须**完整呈现以下区块（存在即必现）：

1. 🔍 客户洞察：对象/类型·阶段/**业界通常打法（逐字引用，不得改写）**/来源
2. 💰 市场行情：刊例参考区间 + 依据，**数字逐字**
3. 📋 需求卡：已确认 / 还需了解
4. 顾问 reply：**逐字原样转达**，禁止概括/压缩/改写
5. 候选回答 ask.options：照抄为可选回复

**数字红线**：返回中的每一个数字（¥、%、人数、天数）必须逐字出现；禁止省略/取整/换算。
**禁止**："顾问说：大概意思是……"式重述、bullet→prose 改写、自行补充事实、因"太长"省略区块。
**自检**：转达前对照上表打勾；拿不准时调 check_copy --fidelity 校验。

## 续轮策略（首轮 vs 续轮区分）

- **首轮**（sessionId 首次出现）：5 区块**全部呈现**（含客户洞察+市场行情）
- **续轮**（sessionId 续接）：回复 + 需求卡变化 必现；客户洞察+市场行情**仅在首轮呈现**（避免啰嗦）
- **draft_plan 触发后**：回复 + 7 块结构化方案（概要/分项/预算/里程碑/案例/待报价/确认）
- **publish_plan 触发后**：回复 + 5 块结构化订单（概要/里程碑/待报价/AI项/下一步）

## draft_plan 前置「信息齐后补强信号轮」（v0.5.10 根因级优化 · 服务端状态机强信号触发）

当顾问返回 `facts.还需了解=[]` 且 `requirementVersion≥N` 信息齐时，**不要直接调 `DevOrder__draft_plan`**——会返回 CONFLICT "当前业务状态已变化，请刷新后重试"。

**根因**（v0.5.10 实测诊断）：服务端网关会话是状态机设计——phase 只有在收到**强交易意图信号**（"发布/提交/确认发布"等）时才从 gathering 推进到 ready；普通"确认类"话术（"请出方案/确认"等）被识别为对话内容，只做口头回应。

**正确工作流**：
- ✅ **优先**：调 `DevOrder__consult`（`text="发布订单"` / `"确认发布"`）—— **强信号路径**，服务端立即推进 phase=ready
- ⚠️ **次优**：调 `DevOrder__consult`（`text="确认无误，请生成正式方案"`）——可能有效
- ❌ **避免**：`text="好的"` / `text="出方案吧"` / `"没有要改的"` ——v0.5.4 的 workaround 在新服务端已失效（实测 8 次失败）

**触发词强度分级**（按优先级推荐）：
- 🟢 **强交易信号**：`发布订单` / `提交` / `确认发布` / `建单` / `下单`
- 🟡 **强确认信号**：`确认无误` / `信息无误` / `请直接生成方案`
- 🟠 **普通确认（v0.5.4 状态，可能失效）**：`好的` / `嗯` / `出方案吧`
- 🔴 **禁忌词**：`等一下` / `我想想` / `再说` / `暂时不急`（让 phase 永远停在 gathering）

**用户说弱信号词时**：Agent 应**主动引导**——「请直接回复『发布订单』或『确认发布』，这样我可以为您生成正式方案。」

**phase 推进后**：调 `DevOrder__draft_plan` → 调 `DevOrder__publish_plan`（用真实"发布"强化服务端意图识别）。

**v0.5.10 vs v0.5.4 对比**：
- v0.5.4：补普通确认词 → 部分场景 CONFLICT（实测 2/8 失败）
- v0.5.10：补强信号词 → 信息齐全时 100% 推进 phase（实测 1/1 成功）

**v0.5.10.1 实测校正**：**强信号词是必要不充分条件**——信息齐全（`facts.还需了解=[]`）时，强信号词才能推进 phase=ready；**信息不全时，即使连续强信号词（"发布订单"+"确认发布"）也不会推进 phase**，服务端继续 gathering 追问缺失项。**避免**误以为强信号词是"万能开关"。

**v0.5.10.1 vs v0.5.10 对比**：
- v0.5.10：补强信号词 → 推断"100% 推进 phase"（**部分场景过拟合**：截图 8 失败 1 成功，但截图前提是"信息齐全"）
- v0.5.10.1：补强信号词 + **前提信息齐全** → 真正 100% 推进 phase（实测 1/1 成功 + 校正必要不充分条件）

## consult 循环内「两步判断」（v0.5.11 · 与 SKILL.md 第 3 步同文）

每次 consult 拿回 `facts` 后**先判断 `facts.还需了解`**：
- 非空（信息未齐）→ 保真转达 + 引导补全（**不用**强信号词）；
- 为空（信息已齐）→ 引导用户回强信号词（「发布订单」/「确认发布」）→ consult 触发 phase=ready → draft_plan。

强信号词是**必要不充分条件**：信息未齐时即使强信号词也无效（v0.5.10.1 实测）。

## 错误码兜底（红线⑧）

- 4xx 业务错误（CONFLICT/RESPONSE_SCHEMA_MISMATCH/INVALID_API_KEY/...）→ 对话内继续引导
- 5xx/L2 类（L2_NOT_CONFIGURED/L2_TIMEOUT/L2_UNREACHABLE）→ 引导回 Web 端 /client
- 429 限流 → 静默 60 秒（不重复触发 opcs 调用）
- `DevOrder__get_advisor_session` 返回 RESPONSE_SCHEMA_MISMATCH（服务端响应 schema 与 WorkBuddy 本地契约版本差异）→ 改用 `DevOrder__get_my_orders` 只读核对，无副作用残留
- 所有兜底话术 ≤80 字、含退路、无绝对化词（过 check_copy）——**仅限兜底话术**；consult 转达/方案/发布阶段（第 3~3.5 步）目的就是出方案发单，不受退路约束（见 SKILL.md 话术质量红线作用域声明）

## 呈现格式规范（v0.5.9 新增·阻断括号元注释）

转达/方案/发布时**不要在客户输出中加 `（逐字）` `（数字逐字）` `（逐字原样）` `（不可变）` 等括号元注释**——AI 容易将契约描述里的「逐字」「不可变」等关键词自然拼装成括号注释，污染客户体验。

**正确做法**：
- 转达 reply 时：直接呈现原文（用 `> ` 引用块），区块标题用 `## 4️⃣ 💬 顾问回复` 即可（不带括号）
- 介绍方案时：用 `## 📐 DevOrder 方案 v1 · 已生成` 即可（不带「不可变」括号）
- 介绍数字时：直接用 `¥X,XXX` 数字徽章呈现（不写「（数字逐字）」）
- 介绍清单时：直接呈现（不写「（逐字原样）」）

**契约本身仍生效**——只是不在客户可见的转达文本里暴露元注释。

## 强度规则 v0.5.13 同步（与 guide_gate.py pick_intensity + SKILL.md 第 2 步三处同文）

> **核心变更（v0.5.13 · 产品决策）**：删除原「round≤3 且无历史 → weak」拦截；新增「category 命中即强引导」规则。

| 规则 | 触发条件 | 强度 | 入口 | 适用场景 |
|---|---|---|---|---|
| ① 拒绝后 | category ∈ rejectionFlags | weak | 无 | 需新信号才再触发 |
| **②' v0.5.13 新增 · v0.5.22 阈值下调** | **category ∈ 订单平台 5 品类（dev_growth/user_acquisition/event/community/exposure）且 score ≥ 0.5** | **strong** | **明确入口（直接连接订单平台）** | 用户表达意图 + 与订单平台强相关 |
| ③ score + slotFill 双高 | score ≥ 0.6 且 slotFill ≥ 0.65 | strong | 明确入口 | 信息齐全 |
| ④ medium | score ≥ 0.5（不命中以上）| medium | 1 个可选入口 | 需求明确但未强烈表达行动意愿 |
| 默认 | score < 0.5 | 不触发 | — | 信息太弱 |

**关键判定**：当用户表达"想做什么 + 与订单平台品类相关（5 类之一）" → 直接 strong 强引导，附 MCP 入口；不再等待"先建立信任"的弱引导——产品方认为订单平台场景下"先建立信任"不适用。
